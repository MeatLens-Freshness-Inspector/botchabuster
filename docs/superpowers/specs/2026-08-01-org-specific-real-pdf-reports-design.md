# Organization-Specific Real PDF Reports Design

## Summary

Replace the current frontend "open HTML and print" export flow with a real frontend PDF generation system for both inspector and admin reports. The new system must produce actual `.pdf` files, not printable HTML, and must support three distinct organization-specific report layouts:

- Gordon College CCS (GCCCS)
- Department of Trade and Industry (DTI)
- City Veterinary Office of Olongapo

Every report must always contain the meat report section. Organization-specific sections appear first, and their visual layout, framing, section order, and emphasis differ by organization.

## Problem Statement

The current report exports are structured like printable web pages. Even after adding organization-specific letterhead asset selection, the report output still behaves like HTML with branding attached. That does not match the target style shown in the GCCCS sample PDF.

The GCCCS sample demonstrates the actual target:

- document-style page composition
- fixed top branding and bottom framing
- repeated page identity across pages
- content arranged inside a document body rather than a web card layout
- polished, deterministic PDF output

The current implementation does not satisfy those requirements because:

- it does not create real PDF files directly
- it relies on browser print behavior
- it uses report HTML as the source artifact
- it treats the letterhead as an attached or embedded asset rather than part of the composed page

## Approved Scope

This design covers both report types:

- inspector report
- admin report

Both report types will use the same document system and rendering pipeline, but with different data depth and organization-specific first sections.

This design does not add new product data sources. All sections must use existing real data already available in the frontend today.

## Product Rules

### Output rules

- Reports must be actual PDF files generated by the frontend.
- Reports must not rely on "open HTML and print to PDF."
- Reports must not embed a PDF letterhead object as a separate visual block.
- Reports must compose the page directly inside the PDF renderer.

### Organization rules

- Every organization gets a distinct PDF layout.
- The GCCCS sample is the only full layout reference.
- DTI and City Vet layouts will be derived from their letterheads and organization purpose.
- Meat report content must always be present for every organization.

### Content rules

- Use only existing real data.
- No placeholder metrics.
- No invented sections.
- If a desired section cannot be supported by existing data, simplify or omit that part instead of fabricating content.

## Shared report backbone

All generated PDFs share this backbone:

1. Organization-specific page frame
2. Organization-specific opening section
3. Shared meat summary section
4. Shared meat detail section
5. Supporting appendix-style tables when necessary

The backbone is shared, but each organization controls:

- branding and header treatment
- footer treatment
- section order
- title language
- section emphasis
- color accents and typographic hierarchy

## Organization-specific opening sections

### GCCCS

GCCCS reports open with a technical or system-related section first.

The section should emphasize existing real analytics such as:

- inspection volume
- confidence trends
- classification distribution
- inspector activity
- location activity
- flagged deviations
- daily trend behavior

This section should feel like a technical or system analytics document before transitioning into the meat reporting body.

### DTI

DTI reports open with market-service and operational oversight framing first.

The section should emphasize existing real metrics such as:

- inspection throughput
- location activity
- unique inspector participation
- spoiled rate
- flagged deviation frequency
- daily operational trend

This section should read like operational and service oversight rather than technical analysis.

### City Veterinary Office

City Vet reports open with veterinary and meat-safety framing first.

The section should emphasize existing real metrics such as:

- meat type distribution
- spoilage and freshness patterns
- protocol-related failures
- flagged deviations
- storage, light-color, area-clean, certificate, and expiry-related evidence where present

This section should read like meat-safety oversight rather than market operations or technical analytics.

## Shared meat section behavior

The meat section must appear in every organization's report.

The core structure should remain shared:

- meat inspection summary
- classification or safety overview
- detailed inspection evidence

Wording and emphasis may be slightly reframed per organization, but the factual structure remains grounded in the same source data.

## Report-Type Differences

### Inspector report

Inspector reports are:

- single-day
- inspector-scoped
- lighter on aggregate analytics
- heavier on individual inspection evidence

The PDF should still use the organization's document identity, but with a narrower scope and fewer high-level sections than the admin version.

### Admin report

Admin reports are:

- range-based
- aggregate-heavy
- organization-first in framing
- broader in table coverage

The admin version should be able to open with the organization-specific section, then transition into shared meat reporting and appendices.

## Rendering Architecture

Implement a shared frontend PDF generation pipeline with four layers:

1. Report data adapters
2. Shared report domain model
3. Organization template layer
4. PDF renderer and composer

### 1. Report data adapters

These adapters convert current UI state into normalized report data.

Required adapters:

- inspector daily report adapter
- admin date-range report adapter

Responsibilities:

- gather existing frontend report data
- normalize labels and section-ready values
- keep organization selection separate from content normalization
- avoid presentation concerns

### 2. Shared report domain model

The normalized model should represent the report independent of a specific organization's layout.

It should support:

- metadata
- summary stats
- charts or chart-ready data
- meat overview data
- inspection detail rows
- appendix sections

This model becomes the single source of truth passed into organization templates.

### 3. Organization template layer

Create one template module per organization:

- GCCCS template
- DTI template
- City Vet template

Each template decides:

- which opening section comes first
- how section titles are named
- which shared sections are emphasized or condensed
- page framing and recurring visual identity

Templates must not fetch data directly. They consume the normalized report model only.

### 4. PDF renderer and composer

This layer composes real PDF pages from the template output.

Responsibilities:

- create actual PDF files in the browser
- place repeating header, footer, and page framing
- lay out titles, stat blocks, narrative summary blocks, tables, and evidence blocks
- repeat table headers after page breaks
- split long detail sections across pages cleanly
- keep layout deterministic across machines

## Layout Rules

The new PDFs should follow document-layout rules derived from the GCCCS sample:

- fixed page size layout
- repeated document framing on all pages
- stable top brand area
- stable bottom footer strip or contact area where appropriate
- content body with predictable margins
- no card-dashboard appearance
- no web-app-style floating panels as the primary composition pattern

### Pagination rules

- Long tables must page-break cleanly.
- Repeated table headers are required after breaks.
- Dense detail should move to later pages or appendix sections.
- First pages should prioritize high-value summary content and organization-specific framing.

## Frontend Technology Direction

Keep the solution in the frontend only.

The implementation may introduce a client-side PDF generation library or renderer, but the architecture must remain frontend-owned. No backend PDF generation endpoint is introduced in this design.

Selection criteria for the renderer:

- reliable browser-side PDF output
- deterministic page layout
- support for repeated page structure
- support for controlled table pagination
- support for images and branding assets

## File and Module Direction

Introduce a focused report-generation area under the frontend codebase.

Suggested structure:

- `frontend/src/lib/reports/`
  - shared types
  - data normalization
  - shared section builders
- `frontend/src/lib/reports/templates/`
  - `gcccs`
  - `dti`
  - `cityVet`
- `frontend/src/lib/reports/pdf/`
  - PDF document builder
  - layout primitives
  - pagination helpers
  - asset helpers

Current report hooks should stop generating raw HTML directly and instead call the new PDF export path.

Primary entrypoints to refactor:

- `frontend/src/pages/user/history/hooks/useHistoryPage.ts`
- `frontend/src/pages/admin-dashboard/hooks/useAdminDashboardPage.ts`

Current HTML builders to retire or replace:

- `frontend/src/pages/user/history/utils/historyPage.ts`
- current admin HTML export construction in `frontend/src/pages/admin-dashboard/hooks/useAdminDashboardPage.ts`

## Migration Strategy

Use an incremental migration with the final goal of removing HTML-print PDF generation.

Suggested sequence:

1. Build normalized report models from existing inspector and admin data.
2. Introduce organization-template selection.
3. Implement PDF renderer primitives and asset loading.
4. Implement the GCCCS template first using the sample PDF as reference.
5. Derive DTI and City Vet templates from their letterheads and approved framing.
6. Wire inspector export to real PDF output.
7. Wire admin export to real PDF output.
8. Remove old "open HTML and print" PDF export code.

## Testing and Verification

### Functional verification

- Unit test report model normalization.
- Unit test organization template selection.
- Unit test presence and order of organization-specific sections.
- Unit test that the meat section is always present for all organizations.

### Visual verification

Because layout is a product requirement, rendered PDF review is part of done.

Verification must include:

- render generated PDFs
- inspect page framing
- inspect section ordering
- inspect table overflow and page breaks
- confirm repeated headers and footers render consistently
- compare GCCCS output against the sample's overall composition style

## Non-goals

This design does not include:

- introducing new backend metrics
- adding placeholder content
- generating PDFs on the server
- keeping the embedded-letterhead-object approach
- preserving the existing report HTML as the main export implementation

## Acceptance Criteria

The design is successful when:

- both inspector and admin exports produce actual PDF files in the frontend
- all three organizations have distinct report layouts
- GCCCS reports begin with a technical or system-oriented first section
- DTI reports begin with market-service and operational framing
- City Vet reports begin with veterinary and meat-safety framing
- every report always includes the meat section
- only existing real data is used
- output looks like composed documents rather than printed web pages
- page framing repeats consistently across multi-page reports
