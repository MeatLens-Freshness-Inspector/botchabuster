# Historical Model Accuracy Design

## Goal

Record model accuracy over time as immutable daily database snapshots and include that history in every generated report format.

## Context

MeatLens currently stores a prediction and confidence on each inspection. Developer metrics derive live accuracy from inspection classifications, but inspections do not identify the model version that produced them. The frontend generates administrator range reports and inspector daily reports as PDF, CSV, and JSON artifacts.

The historical metric must distinguish:

- **Expected accuracy:** the benchmark accuracy declared for a model version.
- **Observed accuracy:** accuracy measured against officially reviewed inspection labels.

The existing `manual_classification` value is initially populated from the prediction, so it is not independent ground truth. Observed accuracy therefore uses only non-null `official_classification` values.

## Goals

- Register model versions with immutable expected benchmark accuracy.
- Associate new inspection predictions with the model version that produced them.
- Capture one immutable accuracy snapshot per model version per previous UTC calendar day.
- Make snapshot creation idempotent and safe to retry.
- Support manual backfills through the same controlled operation.
- Expose snapshot history to authenticated report consumers.
- Include expected accuracy, observed accuracy, evaluation count, and trend data in PDF, CSV, and JSON reports.
- Preserve compatibility with legacy inspections that have no model version.

## Non-goals

- Rewriting or recalculating existing snapshots after they have been finalized.
- Treating unreviewed manual labels as official ground truth.
- Replacing the existing developer training-run metrics or inspection-level confidence metrics.
- Redesigning the administrator or developer dashboard outside the controls needed to register model versions and trigger snapshots.

## Architecture

The feature spans three boundaries:

1. PostgreSQL owns model-version metadata, snapshot immutability, constraints, and accuracy aggregation.
2. The backend owns authorization, model-version registration, snapshot triggering, and typed analytics responses.
3. The frontend fetches the selected date range’s snapshots and passes them through a shared report model so every report adapter and export format uses the same data.

Model registration and snapshot creation are developer-only operations. Snapshot reads are available to authenticated report consumers. The existing service-role Supabase client remains the only database adapter used by the backend.

## Database schema

The implementation creates a new forward-only Supabase migration under `backend/supabase/migrations/`.

### `model_versions`

| Column | Type | Rules | Purpose |
| --- | --- | --- | --- |
| `id` | `uuid` | Primary key, generated by `gen_random_uuid()` | Stable foreign-key target |
| `version_key` | `text` | Required, unique, trimmed and non-empty | Stable deployment identifier sent with inspections |
| `display_name` | `text` | Required, trimmed and non-empty | Human-readable report label |
| `expected_accuracy` | `numeric(5,4)` | Required, between `0` and `1` | Immutable benchmark accuracy |
| `active_from` | `timestamptz` | Required | Start of production use |
| `retired_at` | `timestamptz` | Nullable, after `active_from` | End of production use |
| `created_by` | `uuid` | Nullable foreign key to `auth.users` | Registration audit actor |
| `created_at` | `timestamptz` | Required, defaults to `now()` | Audit timestamp |

Expected accuracy is not updated in place. A revised model or revised benchmark receives a new version key, preserving the meaning of existing snapshots.

### `inspections.model_version_id`

Add a nullable foreign key to `model_versions(id)` with `ON DELETE RESTRICT`. New submissions carry the registered version key; the backend resolves it to the foreign key before insert. Nullable legacy rows remain valid and are excluded from version-specific observed accuracy.

Add an index on `(model_version_id, created_at DESC, id DESC)` for snapshot aggregation and report filtering.

### `model_accuracy_snapshots`

| Column | Type | Rules | Purpose |
| --- | --- | --- | --- |
| `id` | `uuid` | Primary key, generated by `gen_random_uuid()` | Snapshot identity |
| `model_version_id` | `uuid` | Required foreign key to `model_versions(id)` | Model attribution |
| `snapshot_date` | `date` | Required | Previous UTC calendar day represented |
| `expected_accuracy` | `numeric(5,4)` | Required, between `0` and `1` | Benchmark copied at capture time |
| `evaluated_count` | `integer` | Required, nonnegative | Officially labeled predictions in the day |
| `correct_count` | `integer` | Required, nonnegative and no greater than `evaluated_count` | Correct predictions in the day |
| `observed_accuracy` | `numeric(5,4)` | Nullable, between `0` and `1` | `correct_count / evaluated_count`, null when count is zero |
| `created_at` | `timestamptz` | Required, defaults to `now()` | Capture timestamp |

Create a unique constraint on `(model_version_id, snapshot_date)` and an index on `(snapshot_date DESC, model_version_id)`. Enable RLS. The service role writes through the controlled function; ordinary users do not receive direct table access.

Snapshots are append-only. The capture function uses `INSERT ... ON CONFLICT DO NOTHING`; it never updates an existing snapshot. The scheduled job captures the previous UTC day so official labels have a full day to arrive before finalization.

## Snapshot calculation

The migration adds a security-definer PostgreSQL function with the equivalent interface:

```sql
record_model_accuracy_snapshot(
  p_model_version_id uuid,
  p_snapshot_date date
) returns jsonb
```

The function:

1. Validates that the requested date is not in the future and that the model version exists.
2. Selects inspections whose `model_version_id` matches and whose `created_at` falls within the requested UTC date.
3. Counts only rows with non-null `official_classification`.
4. Counts a prediction as correct when `COALESCE(official_classification, classification)` equals the prediction classification; because rows must have an official label for inclusion, this is equivalent to comparing `classification` to `official_classification`.
5. Copies the model version’s expected accuracy into the snapshot.
6. Inserts the snapshot once and returns the existing or newly inserted row as JSON.

The daily scheduler calls this operation for every active model version using the previous UTC date. A developer-only backend operation accepts an explicit date for recovery/backfill, subject to the same no-future and idempotency rules.

## Backend interfaces

Add a model-accuracy area under the existing analytics/developer module boundaries, following the repository’s application/domain/infrastructure/presentation structure.

The read response is an ordered list:

```ts
interface ModelAccuracySnapshot {
  id: string;
  modelVersionId: string;
  versionKey: string;
  displayName: string;
  snapshotDate: string;
  expectedAccuracy: number;
  observedAccuracy: number | null;
  evaluatedCount: number;
  correctCount: number;
  createdAt: string;
}
```

Required operations:

- Developer-only model-version registration with `versionKey`, `displayName`, `expectedAccuracy`, and `activeFrom`.
- Developer-only daily snapshot capture with an optional explicit UTC date for backfills.
- Authenticated snapshot read filtered by `startDate` and `endDate`, ordered by date ascending and then version key ascending.

Registration rejects duplicate version keys, invalid accuracy values, invalid dates, and an active range that overlaps an existing version with the same deployment identity. Snapshot creation reports duplicate rows as successful idempotent results rather than failures.

## Frontend and report integration

Add a typed snapshot client and query it alongside the inspection data used by the report-producing screens.

Extend `ReportDocumentModel` with an optional `modelAccuracyHistory` collection of `ModelAccuracySnapshot` values. Both report adapters call a shared section builder so they expose the same fields:

- A table with date, model version, expected accuracy, observed accuracy, evaluated count, and correct count.
- A line chart with expected and observed accuracy series.
- A clear unavailable marker for observed accuracy when `evaluatedCount` is zero.

The administrator range report uses snapshots between `reportStartDate` and `reportEndDate`. The inspector daily report uses snapshots for `selectedReportDay`. Existing report sections remain unchanged.

Include the same collection in:

- PDF report sections and chart data.
- CSV detail exports as a dedicated historical-accuracy block.
- JSON snapshot exports as `modelAccuracyHistory`.

When there are no snapshots in the requested range, the report retains its normal inspection content and includes an empty-state historical-accuracy section rather than failing generation.

## Access and security

- Keep RLS enabled on both new tables.
- Grant direct table access only to the backend service role.
- Enforce developer authorization in model registration and snapshot-capture controllers.
- Enforce authenticated access and bounded date-range parameters on snapshot reads.
- Use explicit column projections in Supabase queries.
- Validate all numeric values as finite unit metrics (`0` through `1`) at the HTTP and database boundaries.
- Do not allow client-supplied expected accuracy to alter an existing version or snapshot.

## Testing strategy

### Database and backend

- Migration contract tests verify both tables, the inspection foreign key, constraints, indexes, RLS, grants, and the capture function.
- Unit tests verify snapshot response mapping, null observed accuracy, date ordering, range validation, and malformed database rows.
- Unit tests verify model-version registration validation and duplicate handling.
- Unit tests verify snapshot capture authorization and idempotent duplicate results.
- Integration tests verify developer-only writes, authenticated reads, unauthorized access rejection, and bounded date filters.

### Frontend

- Client tests verify the snapshot endpoint, query parameters, and response shape.
- Report adapter tests verify that daily and range reports include the historical-accuracy section and expected/observed series.
- PDF document tests verify the section and empty-state rendering.
- CSV/JSON export tests verify the historical snapshot block is present in both formats.
- Existing report, inspection, and developer dashboard tests must remain green.

## Operational behavior

Before deploying a new model:

1. Register its version key and expected benchmark accuracy through the developer-only operation.
2. Deploy the frontend model configuration with the same version key.
3. New inspections reference that version automatically.
4. The daily scheduler captures the previous day for every active version.

The current deployed model can be registered once with its benchmark value. Older inspections without a version remain valid but are not retroactively attributed to a model. Historical report rows are never rewritten when a later model is registered.
